# How to Design a Problem

[中文版](./README-ZHTW.md)

## Introduction

Designing a problem with this modified TPS consists of five steps:

1. Problem Description
2. Generator
3. Validator
4. Checker
5. Metadata

I'll go through each of these steps. Including the tools that you might find useful.


## 1. Description

In the description, you can follow this recommended way we used in DSA2025 problems. Fields surrounded by `<` and `>` are optional.

```
# Title
## <Modification Notes>
## Problem Description
## <Illustration>
## Input
## Output
## Constraint
## Subtask
### Subtask 1 (10pt)
### Subtask 2 (20pt)
## Sample Testcases
### Sample Input 1
### Sample Output 1
```

Depends on the policy, we might slightly the structure of the description. But generally, it should follow the above format.


## 2. Generator

The generator is a program that generates the test data for the problem. An often ignored, but important property of a generator is determinism. Each time you run the `tps gen` command with the same seed, it should generate the same test data.

To do so, you can use the `jngen.h` in the gen directory. The following is an example of how to use it.

```cpp
#include "jngen.h"

int main(int argc, char* argv[]) {
  // Register the generator. The entire argv will form the random seed.
  registerGen(argc, argv, 1);
  // Parse important parameters from command line arguments
  int n = atoi(argv[1]), m = atoi(argv[2]), q = atoi(argv[3]);
  // Use rnd.next to generate random numbers [2, 15].
  rnd.next(2, 15);
}
```

Next, you should write the `data` file. This file describe how the TPS system use your generator to generate the test data. There are some keywords:

- `@testset`: A testset is a group of testcases.
- `@include`: Include a testset or a testcase.
- `@subtask`: A subtask is a group of testsets. This is how we count the score.
- `manual`: This testset is not generated by the generator. You should provide the input file yourself. Usually, we put the input in the `gen/manual` directory.

**The name of a subtask should start with "subtask" and the name of a testset should not**. This is how our judge system distinguish them.

```
@testset sample1
manual 0-01.in
manual 0-02.in

@testset sample2
manual 0-03.in

@subtask sample
@include sample1
@include sample2
```

To use the generator you write, you should provide the name of the generator as well as the command line arguments. The last argument is a random padding, which provide different test even if the key parameters are the same.

```
@testset 5
gen_sub5 5 300000 100000 bon97dus2
```

If you want to generate a graph, you can consider using the `GraphGen.h` in the `bicycle-parking-tree/gen` directory, or write your own as you please.


## 3. Validator

The validator is a program to check the test input generated by the generator. In general, you should write the validators according to the description of the problem instead of the generator.

You should read the input from the `inf` object.

```cpp
#include "testlib.h"

constexpr int kMaxN = 1e5;

int main(int argc, char* argv[]) {
  registerValidation(argc, argv);
  // Read an integer n with the constraint 1 <= n <= kMaxN. If the input is
  // invalid, the validator will notify you that "n" is invalid.
  int n = inf.readInt(1, kMaxN, "n");
  // Read '\n' at the end of the line.
  inf.readEoln();
  for (int i = 0; i < n; ++i) {
    // Here we pass "u[" + to_string(i) + "]" as the name. If the input u[5] is invalid, the validator will notify you that "u[5]" is invalid.
    int u = inf.readInt(0, n, "u[" + to_string(i) + "]");
    // Read a space after the integer.
    inf.readSpace();
  }
  inf.readEoln();
  // Read the end of the file.
  inf.readEof();
}
```

Of course, you can read other types of input as well, you can use the language server to find the available methods (by typing `inf.read`). Note that you should read everything in the input file. If you forget to read space or `'\n'`, the validator will also report an error.

Sometimes, you might want to check some properties of the input. For example, if the input is a tree. Then you can use `ensure(is_tree(t))` macro, where the `is_tree` function is a checker that returns a boolean value. You should write the `is_tree` function yourself.

To quit the program early, you may also use the `quitf` function. The following is an example:

```
inf.quitf(_fail, "Unknown operation %d", op);
```


## Checker

Usually, we can keep the default checker. But if you wish to write your own. You can refer to the `checker.cpp` in the `bicycle-parking-tree/checker` directory.

If your problem allows multiple correct answers, you may have to read the input and the user output from `inf` and `ouf`. Or else, you can just read the answer and the user output from `ans` and `ouf`. Detail logic is up to you.

Same as the validator, you can use `inf|ouf|ans.read` to find available reading methods.

```cpp
string j;
// Read a word (until meet space|tab|newline) from the user output and store it in j.
ans.readWordTo(j);
```

You can use `quitf` to report the result of the checker.

```cpp
// WA
quitf(_wa, "%d%s words differ - expected: '%s', found: '%s'", n, englishEnding(n).c_str(),
                  compress(j).c_str(), compress(p).c_str());
// AC
quitf(_ok, "%d tokens", n);
```

If you wish to report a partial score, contact us.


## Metadata

There are two metadata files: `problem.json` and `judgemeta.json`.

### problem.json

The `name` and the `code` fields should not contain any space. The `time_limit` is in seconds and the `memory_limit` is in megabytes. The `score_policy` is `sum` during the DSA course, this is currently the only method. This means the subtask sum instead of a direct sum from each testcase.

```json
{
    "name": "BicycleParkingTree",
    "code": "bicycle-parking-tree",
    "title": "Bicycle Parking Tree",
    "type": "Batch",
    "time_limit": 1.0,
    "memory_limit": 2048,
    "score_policy": "sum",
    "has_grader": false,
    "java_enabled": false,
    "python_enabled": false
}
```

### judgemeta.json

The `full_score` is the total score of the problem. The `tags` and `problemRelatedTags` are used for problem recommendation, you can ignore them during the DSA course. The `allowed_languages` is the list of languages that the problem allows. In DSA, usually we only allow `C`. The `process_limit` is the maximum number of processes that the user's solution can create. In DSA, this is usually 1. The `dailyQuota` is the maximum number of submissions that a user can submit in a day.

```json
{
  "full_score": 100,
  "tags": [
      "basic"
  ],
  "problemRelatedTags": [
      "math"
  ],
  "allowed_languages": [
      "gcc c17",
      "gcc c23"
  ],
  "process_limit": 1,
  "dailyQuota": 5
}
```
